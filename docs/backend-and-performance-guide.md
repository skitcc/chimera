# Как устроены Chimera и нагрузочное тестирование

## Приложение и служебные компоненты

Рабочий React-интерфейс: http://chimera.192.168.49.2.nip.io/legacy/ . Корень сайта — статическая страница edge. Swagger: http://chimera.192.168.49.2.nip.io/api/v1/docs/index.html . Проверка зависимостей Gateway: http://chimera.192.168.49.2.nip.io/ready .

Основной путь API: браузер → Ingress → edge → Gateway → gRPC-сервис → база. Файлы идут отдельным путём: браузер → S3 Ingress → RustFS.

| Компонент | Назначение |
| --- | --- |
| Gateway, 3 пода | REST, JWT, ограничение авторизации, вызовы Identity/Catalog/Social |
| Identity, 3 пода | Пользователи, bcrypt-пароли, вход и выпуск JWT |
| Catalog, 3 пода | Метаданные треков, публикация, временные ссылки на файлы |
| Social, 3 пода | Лайки, подписки, плейлисты; вызывает Catalog и Identity |
| PostgreSQL primary | Три отдельные базы/роли сервисов; запись и необходимые свежие чтения |
| Две PostgreSQL-реплики | Асинхронное WAL-копирование primary; разрешённые чтения |
| RustFS | Файлы через S3 API. В PostgreSQL лежат метаданные, а не содержимое аудио |
| Kafka | Асинхронные события удаления между независимыми базами |
| kafka-topics Job | Создаёт топики один раз. Completed — нормальное завершение |
| Ingress nginx | Принимает внешние имена/HTTP и выбирает вход в приложение или RustFS |
| edge nginx, 2 пода | Маршрутизация /api, /legacy, /monitoring, /admin и собственная статика |
| web nginx | Отдаёт собранный React; страница в браузере обращается к API |
| mirror | Дополнительная сборка клиента с префиксом /mirror, общий backend |
| Adminer | Служебный интерфейс просмотра SQL-базы |

Числа подов относятся к Kubernetes-манифестам. Compose — более простой локальный стек: по экземпляру сервисов, PostgreSQL, хранилище, Kafka и web; полный Kubernetes-мониторинг в нём не описан.

### Зачем S3

S3 — название API объектного хранилища; у тебя его реализует локальный RustFS, без обязательного обращения к Amazon.

При загрузке Catalog создаёт запись трека и выдаёт временную подписанную ссылку. Клиент пишет файл напрямую в RustFS, затем подтверждает публикацию через Catalog. При воспроизведении API выдаёт redirect на временную ссылку, и клиент читает файл напрямую из хранилища. Поэтому байты музыки не прокачиваются через Go Gateway/Catalog.

В тесте `stream` — получение ссылки через Catalog, `stream-body` — чтение файла из RustFS, `upload` — запись в RustFS. Это разные операции с разными причинами задержки.

### Зачем Kafka и outbox

У сервисов отдельные базы. Удаление пользователя в Identity не может обычным SQL foreign key удалить строки из Catalog/Social.

Identity удаляет пользователя и записывает UserDeleted в outbox в одной транзакции. Фоновый relay отправляет событие в Kafka. Catalog/Social читают его и чистят свои сущности. Catalog также публикует TrackDeleted; отдельный обработчик удаляет объект, Social удаляет связанные лайки/позиции. processed_events защищает от повторного применения события.

Если Kafka или потребитель временно недоступны, фоновая работа отстаёт и затем догоняет. API может оставаться доступным. Consumer lag — число ещё не обработанных сообщений. Уменьшение задержек API не доказывает, что этот lag уже вернулся к нулю.

Реплики PostgreSQL помогают чтениям, но здесь нет автоматического выбора нового primary при его отказе. Один minikube-узел и один Kafka-брокер также не образуют отказоустойчивый многосерверный кластер.

## Наблюдаемость: что именно показывает каждый инструмент

| Инструмент | Что хранит/делает | Пример вопроса |
| --- | --- | --- |
| Prometheus | Числовые временные ряды | Как менялись RPS, ошибки, CPU, lag? |
| Grafana | Интерфейс к источникам данных | Где смотреть метрики, логи и трассы вместе? |
| Loki | Логи приложения | Какую ошибку написал Catalog? |
| Promtail | Доставляет stdout/stderr подов в Loki | Как строки попадают в централизованные логи? |
| Tempo | Трассировки запросов | На каком участке REST → gRPC → SQL/S3 потрачено время? |
| OpenTelemetry Collector | Принимает, группирует и пересылает трассы в Tempo | Куда сервисы отправляют spans? |
| postgres-exporter | Преобразует данные PostgreSQL в метрики | Насколько отстают standby? |
| kafka-exporter | Метрики брокера/consumer groups | Накапливается ли очередь событий? |
| cAdvisor внутри kubelet | Метрики контейнеров | Сколько CPU/RAM потребляет весь контейнер? |

Обычный Prometheus опрашивает /metrics каждого Go-пода и exporters каждые 5 секунд. Тестовый Prometheus опрашивает cAdvisor и получает remote write от k6. Это разные наборы данных. Для итоговой HTTP-статистики тест использует исходный samples.json.gz, а не приближённые перцентили Prometheus.

Включённая обычная Grafana доступна по /monitoring/. Для работы страницы нужны её deployment и источники. В момент проверки постоянные Prometheus/Grafana/Loki/Tempo/Collector были масштабированы в 0 старым стендом; API и web работают. Логи всё равно можно читать через kubectl. Ошибка экспорта OTel при выключенном Collector сама по себе не означает ошибку пользовательского запроса.

### Зачем отдельный Prometheus при тесте

Отдельная Grafana текущим runner **не запускается**. PNG строит plot.py.

Отдельный Prometheus даёт независимую конфигурацию, частоту сбора и время жизни измерений. Он работает снаружи minikube, может быть закреплён на CPU наблюдения и собирает CPU/RAM даже при выключенном обычном мониторинге. Перед нагрузкой runner проверяет настоящий scrape cAdvisor. После выгрузки JSON и графиков контейнер удаляется.

Использовать один постоянный Prometheus технически можно, если добавить нужные источники и учесть его влияние. Отдельный экземпляр — выбор организации эксперимента, не обязательное условие работы k6. Он не устраняет нагрузку обычного мониторинга, если тот тоже включён внутри minikube.

## Сборка и запуск

Go workspace backend/go.work объединяет сервисы, contracts, platform, testkit и e2e. У каждого сервиса свой main.go и Dockerfile.

Внутри Go-сервиса transport принимает HTTP/gRPC/событие, usecase выполняет сценарий, domain содержит правила, infra реализует PostgreSQL/S3. main.go собирает зависимости, применяет встроенные миграции и запускает сервер/фоновые обработчики.

Go Dockerfile использует golang для сборки бинарника и небольшой Alpine для запуска от непривилегированного пользователя. Frontend собирается Node/Vite в dist, затем эти файлы раздаёт nginx. Edge — отдельный nginx-образ с маршрутизацией и статикой.

Первый запуск Kubernetes из корня:

```bash
minikube start
make -C backend k8s-images
make -C backend k8s-up
```

k8s-images собирает образы прямо в minikube. k8s-up создаёт ключи/секреты при необходимости, включает ingress, применяет kustomize и ждёт готовности. **k8s-up не пересобирает образы.** При повторной сборке того же тега :dev уже работающие поды сами не заменятся. Например, после изменения Catalog:

```bash
make -C backend k8s-images
minikube kubectl -- -n chimera rollout restart deployment/catalog
```

Compose для отдельного простого локального запуска: подготовить .env по .env.example и выполнить docker compose up --build. В нём Gateway опубликован на 8080, web — на 5173 при стандартных значениях .env. Это альтернативное развёртывание, а не команда управления уже запущенным minikube.

Kubernetes Deployment управляет репликами stateless-сервиса; StatefulSet — экземплярами с устойчивыми именами и дисками; Service даёт стабильную точку доступа; headless Service отдаёт адреса подов для gRPC round robin. ConfigMap хранит настройки, Secret — пароли/ключи, PVC — запрос постоянного диска, Job выполняет разовую работу.

## Что смотреть при проблеме

```bash
make -C backend k8s-status
curl http://chimera.192.168.49.2.nip.io/ready
minikube kubectl -- -n chimera get pods
minikube kubectl -- -n chimera describe pod ИМЯ_ПОДА
minikube kubectl -- -n chimera logs ИМЯ_ПОДА --tail=100
minikube kubectl -- -n chimera logs ИМЯ_ПОДА --previous --tail=100
```

READY — готов ли под принимать работу; RESTARTS — сколько раз контейнер перезапускался. Исторический ненулевой RESTARTS не доказывает сбой во время последнего теста: нужны время и сравнение до/после. Предыдущие логи полезны для завершившегося контейнера. OOMKilled означает завершение из-за памяти, CrashLoopBackOff — повторные падения, ImagePullBackOff — проблему получения образа.

/ready Gateway проверяет Identity/Catalog/Social. /live проверяет, что сам процесс работает. При этом сервис может быть готов по probe и отвечать слишком медленно для выбранного SLO.

При включённых Loki/Tempo запрос ищется по X-Request-Id/trace_id: трасса показывает путь между сервисами, логи — конкретные ошибки. В k6 исходных точках сейчас нет автоматически сохранённой трассы каждого запроса; HTTP-шаги и время помогают локализовать цепочку, но не доказывают виновность одного сервиса.

## Нагрузочное тестирование

Подготовка конфигурации и измерение разделены:

```bash
make -C backend perf-prepare
make -C backend perf-run PROFILE=quick SCENARIO=trio
```

trio последовательно выполняет ramp → stress → soak. Quick: 2 + 2 + 1 минута нагрузки; full: 10 + 10 + 10 минут. all дополнительно запускает soak с 10% и 20% некорректных действий. Сценарии не выполняются параллельно на одном стенде.

Runner проверяет готовность и повышенный лимит авторизации, создаёт один уникальный dataset, запускает наблюдение, затем k6, анализ и уборку своих данных. PostgreSQL/Kafka/RustFS не пересоздаются и PVC не очищаются. На время кластера могут влиять другие процессы; конфигурация записана в environment.json.

Слушатели читают ленту/карточки/файлы и лайкают; подписчики открывают профили/подписки/плейлисты; авторы загружают, публикуют и удаляют треки. Пропорции VU примерно 60/25/15 с округлением. Паузы фиксированы, каждый цикл заново выполняет вход. Это достаточно интенсивная нагрузка на авторизацию; реальный клиент может гораздо дольше использовать один JWT.

VU — число активных цепочек, RPS — число завершённых HTTP-запросов в секунду. Часть HTTP идёт напрямую в RustFS. В отчёте поэтому отдельно есть API RPS и общий HTTP RPS. Если ответы замедляются, VU ждут и завершённый RPS может перестать расти. Этот тест не поддерживает заданную независимую интенсивность входящих запросов.

Сохранённые исходные samples.json.gz позволяют повторить расчёты без нагрузки.

## При каком RPS начинаются проблемы

Различай три события:

- Нарушение SLO: например, p95 выше 500 мс, но все HTTP-ответы корректны.
- Неожиданные ответы: 5xx, таймауты, неожиданные 4xx. Ожидаемая 404 от специально ошибочного шага не является отказом.
- Падение процесса: рестарт/OOM/CrashLoop, подтверждённые Kubernetes и логами.

В knee.json у ступени есть VU, RPS, p95, error_rate, failure_reasons и operations. Сначала найти ступень с нарушением, затем windows.json для времени и http.json/operations для проблемных шагов. login ведёт к Identity; feed/card/create — к цепочке Catalog; likes/follow/playlists — к Social и его зависимостям; upload/stream-body — непосредственно к RustFS. Связанный gRPC/SQL-вызов может быть реальной причиной — для этого нужны трассы и логи.

Успешная ступень A и неуспешная B ограничивают диапазон, а не устанавливают точный универсальный предел RPS. Состав операций, CPU, размер файлов, кэш и соседняя нагрузка должны быть одинаковыми. Для уточнения диапазона нужен отдельный длительный прогон около границы, а не вывод по единственной короткой ступени.

## Что означает recovered

Stress держит базу B, затем ceil(1.6 × B), затем B. p95 базы считается по первой фазе без прогрева. После снятия перегруза ищется первое полное 1-секундное окно, где доля неожиданных отказов <1%, а p95 ≤1.2 базового p95. Время считается до конца этого окна. У Quick после перегруза 60 секунд наблюдения; у Full — 240.

Это один общий критерий API. Он не проверяет CPU, RAM, Kafka lag, состояние каждого микросервиса и длительную устойчивость. Отдельное автоматическое время восстановления каждого сервиса сейчас не рассчитывается. Если перегруз вообще не вызвал ухудшения, overload_degraded=false помогает не называть этот результат восстановлением после отказа. Если здоровое окно не найдено, recovered=false означает отсутствие подтверждения в заданном времени, а не вечный отказ.

### Фактический сохранённый stress

Прогон 20261119T132220Z-c61f1d: 50 → 200 → 50 VU.

| Фаза | Общий HTTP RPS | API RPS | p95 | Ошибки |
| --- | --- | --- | --- | --- |
| База, 50 VU | 31.00 | 28.70 | 78.66 мс | 0% |
| Перегруз, 200 VU | 120.40 | 109.40 | 544.07 мс | 0% |
| Возврат, 50 VU | 33.05 | 29.75 | 76.92 мс | 0% |

Порог восстановления: 78.66 ×1.2 =94.39 мс. В первом полном окне после снятия перегруза p95=64.15 мс, ошибок 0%, поэтому recovery_sec=10. Это обнаружение нормального окна через 10 с, а не измерение точного физического момента с точностью до миллисекунды. Сервисы по HTTP не отказывали; наблюдалось замедление.

Сохранённый ramp до 240 VU дал около 149 общих HTTP RPS с нулевыми отказами; его предел не найден. Отличие от stress не противоречие: это разные короткие эксперименты с разной историей нагрузки, кэшем и внешним I/O. Их нельзя свести к утверждению «при 120 RPS сервис всегда падает».

Важно: в этом stress после первого здорового окна p95 снова был 258.38 мс на 80-й секунде и 117.01 мс на 120-й, при пороге восстановления 94.39 мс. Поэтому no_observed_relapse=false. Эти всплески не нарушают общий SLO 500 мс, но нарушают более строгий критерий возврата к исходной скорости. recovery_sec=10 нельзя интерпретировать как устойчивое восстановление до конца наблюдения.

График rps_over_time.png возвращён по запросу: X — секунды, Y — завершённые HTTP-запросы/с за 10-секундное окно; отдельные линии показывают все HTTP и только API без прямого S3. На временных графиках длительности фаз вынесены в верхнюю полосу, значимые события обозначены цифрами с расшифровкой под графиком; вертикальные подписи не накладываются.
