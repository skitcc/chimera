# Нагрузочное тестирование

Нагрузочный тест измеряет уже работающий minikube. Он не развёртывает приложения, не масштабирует их и не удаляет PVC, PostgreSQL, Kafka или S3. Подготовка стенда — отдельная операция.

```bash
# Один раз применить конфигурацию perf: обычный стек, AUTH_RATE_LIMIT=100000.
make -C backend perf-prepare
# Проверить готовность без seed, нагрузки и изменения инфраструктуры.
PREFLIGHT_ONLY=1 make -C backend perf-run
# Одна серия: ramp, stress, soak без ошибок / с 10% / с 20% ошибочных действий.
make -C backend perf-run PROFILE=quick SCENARIO=all
# Вернуть обычную конфигурацию, включая лимит авторизации.
make -C backend perf-restore
```

Нужны работающий minikube, Docker, Python 3 и matplotlib. Sudo для обычного запуска не нужен. Подготовка применяет kustomize явно, блокируется во время измерений и сохраняет все данные. `reset.sh reset` больше не поддерживается. Остановка и пересоздание базы не являются частью нагрузочного сценария.

## Жизненный цикл

`run.sh` передаёт управление `runner.py`. Один процесс владеет блокировкой серии и проходит следующие этапы:

1. **Preflight:** проверяет все девять рабочих нагрузок Kubernetes, готовность желаемых реплик, ошибки CrashLoop/ImagePull, лимит авторизации и реальный GET через edge. Ожидание ограничено `READY_TIMEOUT=90` секундами. При ошибке сохраняет статусы, события, текущие и предыдущие логи; k6 не запускает.
2. **Seed:** создаёт уникальные для серии 50 пользователей, 40 готовых треков по 256 КиБ и 5 плейлистов через API. Авторизует каждого автора один раз. Ждёт видимости опубликованных треков. Один `dataset.json` используется всеми сценариями; имена не конфликтуют с предыдущими прогонами.
3. **Наблюдение:** запускает собственные kubectl proxy и Prometheus на свободных портах. Проверяет реальный scrape cAdvisor. Имена контейнеров уникальны; работающие сторонние контейнеры не удаляются. Внутрикластерный мониторинг остаётся в исходном состоянии.
4. **Измерение:** последовательно запускает k6. Получает его код завершения непосредственно от Docker CLI. При первой ошибке прекращает серию. Stress/soak серии используют устойчивую ступень её ramp, а не файл от предыдущего запуска.
5. **Отчёт и уборка:** сохраняет исходные HTTP-точки, собирает ресурсы, строит графики, удаляет только созданные этой серией контейнеры/процессы и тестовых пользователей. Удаление пользователей очищает их сущности через события. Неуспешная уборка видна в stderr; идентификаторы тестовых данных остаются в dataset.json. Инфраструктура продолжает работать.

Seed, уборка и подготовка исключены из HTTP-измерений. Прогрев — 10 секунд quick и 30 секунд full. CPU/RAM/диск отчёта относятся к измеряемой фазе. Остальные процессы хоста и мониторинг могут влиять на результаты; это отражается в `environment.json`.

## Сценарии и роли

| Сценарий | quick | full |
| --- | --- | --- |
| ramp | 10, 25, 50, 100, 160, 240 VU по 20 с | Те же ступени по 100 с |
| stress | База / четырёхкратная база / база, 30/30/60 с | 180/180/240 с |
| soak | Постоянная база 60 с | Постоянная база 10 мин |

Отдельный сценарий: `SCENARIO=ramp|stress|soak`, для stress/soak `STABLE_VUS=10` по умолчанию. `FAULT_RATE=0|0.1|0.2` задаёт вероятность некорректного действия на поддерживаемом шаге, а не долю всех HTTP-запросов. В `all` ошибки добавляются только в soak.

Примерно 60% VU — слушатели (вход, лента, карточка, стрим и чтение объекта, лайк, любимое), 25% — подписчики (вход, пользователи, автор, треки, подписка и плейлисты), остальные — авторы (вход, загрузка и публикация, создание плейлиста, удаление своего плейлиста и трека). Доли округляются до целых VU. Паузы фиксированы. Аккаунты переиспользуются, поэтому это нагрузка на цепочки API, а не модель уникальных данных каждого VU.

Используется закрытая модель: при медленных ответах VU отправляет меньше запросов. Число VU не равно RPS. Синтетический файл не моделирует полноценный музыкальный стрим и пользовательскую перемотку. `TRACK_BYTES=1048576` меняет размер на 1 МиБ. Десятиминутный full soak — короткая проверка стабильности, для медленных утечек нужен длительный эксперимент.

Ожидаемые 400/401/404 от ошибочных действий корректны. Другой статус или таймаут — неожиданный отказ. У soak порог отказов <1%; ramp/stress допускают перегрузку, чтобы её измерить. Во всех сценариях обязательны измеренные запросы и завершённые сессии.

## Артефакты

Каждая серия получает каталог `perf-results/<UTC-время>-<id>/`, каждый сценарий — вложенный каталог. Старые результаты не перезаписываются.

- `environment.json`, `dataset.json`, `results.json` — контекст стенда, тестовые сущности и коды завершения сценариев.
- `samples.json.gz`, `k6.log`, `run.json`, `analysis.log` — исходные точки и диагностика сценария.
- `http.json` — HTTP-статусы, отказы, точные перцентили по шагам, сессии и байты стрима фазы measure.
- `summary.json`, `throughput.json`, `resources.json` — сводки k6, RPS/сессии/байты и ресурсы контейнеров. PostgreSQL включает primary и обе реплики; CPU указан в ядрах, RAM — в байтах.
- `knee.json`, `recovery.json` — устойчивые ступени ramp и восстановление stress.
- `series/`, `plots/`, `compare/` — сохранённые временные ряды, семь PNG и числовое сравнение soak в compare.json.

HTTP-отчёт строится по исходным точкам, без зависимости от доставки remote write. Отчёт ресурсов использует Prometheus; сохранённые серии позволяют повторить анализ после его остановки. Отсутствие запросов, сессий или CPU/RAM является ошибкой анализа. Ошибочные/незавершённые прогоны не сравниваются как успешные.

Перцентили ступени считаются по её запросам, а не средним оконным p95. Временные графики используют 1-секундные окна. Устойчивая ступень: отказы <1%, p95 ≤ `LATENCY_SLO_MS` (по умолчанию 500 мс), RPS растёт с VU. Относительный скачок p95 — предупреждение, а не самостоятельное доказательство предела. Если все ступени прошли, `capacity_found=false`: определён максимум проверенной нагрузки, а не предел системы. Для восстановления требуется полное окно после перегруза с отказами <1% и p95 ≤1.2 от базы. Quick даёт предварительную оценку, а не доказанную производственную ёмкость.

## Изоляция CPU

По умолчанию runner не меняет CPU minikube. `sudo ISOLATE_CPUS=1 make -C backend perf-run ...` включает существующий механизм cpuset/systemd **после** preflight. В этом режиме minikube получает 0–3, k6 — 4–5, наблюдение — 6–7 при ≥8 CPU; при 4–7 CPU генератор и наблюдение получают по одному CPU. Уборка возвращает исходный cpuset. Диск и память остаются общими; cpuset не запрещает прочим процессам хоста работать на тех же CPU.

## Проверки

```bash
python3 -m unittest discover -s deploy/perf -p 'test_*.py'
```

CI проверяет расчёты, запрет запуска нагрузки при неготовом стенде, остановку серии при сбое, а также запуск primary без внутреннего watchdog и атомарную публикацию клона реплики. Для этого не требуется запускать кластер или стирать данные.

## Три прогона и обязательные графики

`make -C backend perf-run PROFILE=quick SCENARIO=trio` выполняет ramp → stress → soak без ошибочных действий. Это 5 минут заданной нагрузки плюс seed, завершение итераций и анализ. Full trio — 30 минут. Выполнение последовательное: одновременные эксперименты на одном стенде смешали бы нагрузку. `all` сохраняет пять прогонов, включая ещё два soak с ошибками.

В `plots/`: `latency_over_time.png` показывает p50/p75/p90/p95/p99 во времени; `latency_distribution.png` — распределение всех запросов по рангу/доле с отметками пяти перцентилей; `latency_percentiles.png` — столбцы пяти перцентилей; `latency_histogram.png` — число запросов в интервалах задержки. Все построены по phase=measure. Время запроса — HTTP-отправка/ожидание/получение, без пауз пользователя; это не длительность всей пользовательской сессии.

## Чтение отказов и восстановления

В plots/ остаются только latency_over_time, latency_distribution, latency_percentiles, latency_histogram, cpu_over_time, ram_over_time и rps_over_time. RPS, ошибки, I/O и прочие числовые данные сохраняются без дополнительных графиков. Старые известные лишние PNG удаляются при повторном анализе; исходные измерения не удаляются.

`report.md` — читаемая сводка; `knee.json` содержит VU, общий HTTP RPS, API RPS без прямых S3-запросов, p95, ошибки, причины нарушения и проблемные операции каждой ступени. `windows.json` содержит те же HTTP-операции по 1-секундным окнам. В `http.json` у шагов есть статусы и неожиданные отказы. Это позволяет отличить, например, отказ ленты от отказа загрузки файла.

`recovery.json`: базовый p95 рассчитывается по первой фазе stress без прогрева. После возврата к базовому VU ищется первое полное 1-секундное окно с ошибками <1% и p95 ≤1.2 от базы. Время считается от снятия перегруза до конца этого окна, с шагом 1 с. Отсутствующее окно ошибок не считается здоровым. Это одно окно API, без проверки CPU, RAM, Kafka lag или устойчивости на длительном интервале. `overload_degraded=false` означает, что ухудшение по этому критерию вообще не было зафиксировано. `recovered=false` означает отсутствие подтверждения за 60 с quick / 240 с full после перегруза, а не доказательство вечного отказа.

Нагрузочный runner сейчас запускает отдельный Prometheus и kubectl proxy, без отдельной Grafana. Prometheus нужен для cAdvisor CPU/RAM и получает remote write k6; PNG создаёт plot.py. Обычный Prometheus/Grafana/Loki/Tempo — постоянная наблюдаемость приложения; runner их не выключает и не включает.

`recovery_mode=first_healthy_1s_window` явно обозначает способ расчёта. Поле `relapse_windows` сохраняет последующие окна с новым превышением порога, `no_observed_relapse=false` не позволяет путать первое здоровое окно с устойчивым восстановлением.

График rps_over_time.png возвращён по запросу: X — секунды, Y — завершённые HTTP-запросы/с за 1-секундное окно; отдельные линии показывают все HTTP и только API без прямого S3. На временных графиках длительности фаз вынесены в верхнюю полосу, значимые события обозначены цифрами с расшифровкой под графиком; вертикальные подписи не накладываются.

## Поиск максимальной пропускной способности

```bash
ISOLATE_CPUS=1 make -C backend perf-run SCENARIO=capacity
```

Это отдельный открытый профиль: k6 constant-arrival-rate, одна итерация — один HTTP-запрос, без sleep. Целевой RPS задаётся независимо от времени ответа. Сначала 50, 100, 200, 400… HTTP RPS до нарушения SLO или CAP_MAX_RPS, затем уточнение границы делением интервала и подтверждение последней успешной точки 180 секундами. Между ступенями выполняются три последовательных контрольных раунда чтения Catalog/Identity/Social и авторизации; если они не проходят в течение минуты, поиск прекращается. Инфраструктура и пользовательские данные не сбрасываются.

По умолчанию смесь по числу запросов: 30% лента, 15% карточка, 15% реальный вход, 15% лайк, 10% создание метаданных трека, 5% создание плейлиста, 10% скачивание объекта RustFS. Это отдельные операции, не полные сессии с think time. Записи создаются в аккаунтах серии и удаляются каскадом при её уборке. JWT заранее подготовлены для остальных авторизованных действий; вход в 15% запросов всё равно выполняется через Identity с bcrypt. Файлы — 256 КиБ по умолчанию. Подписанные S3-ссылки обновляются перед каждой ступенью.

Проверяем p95 ≤LATENCY_SLO_MS (500), неожиданные отказы <1%, фактически начатый и завершённый поток ≥98% целевого, dropped_iterations=0. Пропущенные итерации не являются отправленными запросами. При нехватке VU с быстрыми корректными ответами граница помечается неоднозначной. Загруженный ≥90% доступных CPU генератор или отсутствие его телеметрии также не позволяют объявить найденный предел приложения. generator.json содержит замеры CPU k6. Если достигнут только верхний заданный потолок, сообщается нижняя подтверждённая граница, а не выдуманный максимум.

capacity-report.md и capacity.json в корне серии содержат цель, фактические RPS, p95, ошибки, пропуски, подтверждение и границы. Каждая ступень имеет собственные сырые измерения, отчёты, CPU/RAM и графики. Результат относится к зафиксированному составу запросов, объёму данных, CPU, кэшу и окружению; трёхминутное подтверждение не заменяет многочасовой soak.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| CAP_START_RPS | 50 | Начальная точка |
| CAP_MAX_RPS | 1600 | Ограничение поиска сверху |
| CAP_RESOLUTION_RPS | 25 | Ширина уточняемого интервала |
| CAP_STEP_SEC | 60 | Измерение каждой поисковой точки |
| CAP_CONFIRM_SEC | 180 | Длительное подтверждение |
| CAP_WARMUP_SEC | 10 | Прогрев перед каждой точкой |
| CAP_MAX_VUS | 600 | Резерв исполнителей k6, не заданная нагрузка |
| CAP_MAX_TRIALS | 12 | Ограничение числа поисковых точек, кроме подтверждений |
| CAP_WORKLOAD | mixed | mixed или catalog (только GET ленты) |

Длительности capacity задаются этими переменными; PROFILE=quick/full не меняет их автоматически. Для сравнения результатов сохранять одинаковые настройки CPU, состав операций и размер файлов.

Частота сбора тестового Prometheus и iostat — 1 секунда; шаг временных графиков — 1 секунда. CPU рассчитывается через rate за 30 секунд: это сглаженная загрузка, а не мгновенное значение. Частота обновления исходных счётчиков cAdvisor может быть ниже частоты опроса. HTTP-тайм-аут k6 в обычных сценариях и capacity — 5 секунд; превышение учитывается как ошибка, а не удаляется из статистики. Настройки применяются к новым прогонам.
