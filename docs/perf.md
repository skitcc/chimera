# Нагрузочное тестирование

Нагрузочный тест измеряет уже работающий minikube. Он не развёртывает приложения, не масштабирует их и не удаляет PVC, PostgreSQL, Kafka или S3. Подготовка стенда — отдельная операция.

```bash
# Один раз применить конфигурацию perf: обычный стек, AUTH_RATE_LIMIT=100000.
make -C backend perf-prepare
# Проверить готовность без seed, нагрузки и изменения инфраструктуры.
PREFLIGHT_ONLY=1 make -C backend perf-run
# Одна серия: ramp, stress, soak без ошибок / с 10% / с 20% ошибочных действий.
make -C backend perf-run PROFILE=quick SCENARIO=all
# Вернуть обычную конфигурацию, включая лимит авторизации.
make -C backend perf-restore
```

Нужны работающий minikube, Docker, Python 3 и matplotlib. Sudo для обычного запуска не нужен. Подготовка применяет kustomize явно, блокируется во время измерений и сохраняет все данные. `reset.sh reset` больше не поддерживается. Остановка и пересоздание базы не являются частью нагрузочного сценария.

## Жизненный цикл

`run.sh` передаёт управление `runner.py`. Один процесс владеет блокировкой серии и проходит следующие этапы:

1. **Preflight:** проверяет все девять рабочих нагрузок Kubernetes, готовность желаемых реплик, ошибки CrashLoop/ImagePull, лимит авторизации и реальный GET через edge. Ожидание ограничено `READY_TIMEOUT=90` секундами. При ошибке сохраняет статусы, события, текущие и предыдущие логи; k6 не запускает.
2. **Seed:** создаёт уникальные для серии 50 пользователей, 40 готовых треков по 64 КиБ и 5 плейлистов через API. Авторизует каждого автора один раз. Ждёт видимости опубликованных треков. Один `dataset.json` используется всеми сценариями; имена не конфликтуют с предыдущими прогонами.
3. **Наблюдение:** запускает собственные kubectl proxy и Prometheus на свободных портах. Проверяет реальный scrape cAdvisor. Имена контейнеров уникальны; работающие сторонние контейнеры не удаляются. Внутрикластерный мониторинг остаётся в исходном состоянии.
4. **Измерение:** последовательно запускает k6. Получает его код завершения непосредственно от Docker CLI. При первой ошибке прекращает серию. Stress/soak серии используют устойчивую ступень её ramp, а не файл от предыдущего запуска.
5. **Отчёт и уборка:** сохраняет исходные HTTP-точки, собирает ресурсы, строит графики, удаляет только созданные этой серией контейнеры/процессы и тестовых пользователей. Удаление пользователей очищает их сущности через события. Неуспешная уборка видна в stderr; идентификаторы тестовых данных остаются в dataset.json. Инфраструктура продолжает работать.

Seed, уборка и подготовка исключены из HTTP-измерений. Прогрев — 10 секунд quick и 30 секунд full. CPU/RAM/диск отчёта относятся к измеряемой фазе. Остальные процессы хоста и мониторинг могут влиять на результаты; это отражается в `environment.json`.

## Сценарии и роли

| Сценарий | quick | full |
| --- | --- | --- |
| ramp | 100, 200, 300, 400, 500, 650 VU по 20 с | Те же ступени по 100 с |
| stress | База / база ×1,6 / база, 30/30/60 с | 180/180/240 с |
| soak | Постоянная база 60 с | Постоянная база 10 мин |

Отдельный сценарий: `SCENARIO=ramp|stress|soak`, для stress/soak `STABLE_VUS=10` по умолчанию. `FAULT_RATE=0|0.1|0.2` задаёт вероятность некорректного действия на поддерживаемом шаге, а не долю всех HTTP-запросов. В `all` ошибки добавляются только в soak.

Примерно 60% VU — слушатели (вход, лента, карточка, стрим и чтение объекта, лайк, любимое), 25% — подписчики (вход, пользователи, автор, треки, подписка и плейлисты), остальные — авторы (вход, загрузка и публикация, создание плейлиста, удаление своего плейлиста и трека). Доли округляются до целых VU. Паузы фиксированы. Аккаунты переиспользуются, поэтому это нагрузка на цепочки API, а не модель уникальных данных каждого VU.

Используется закрытая модель: при медленных ответах VU отправляет меньше запросов. Число VU не равно RPS. Синтетический файл не моделирует полноценный музыкальный стрим и пользовательскую перемотку. `TRACK_BYTES=1048576` меняет размер на 1 МиБ. Десятиминутный full soak — короткая проверка стабильности, для медленных утечек нужен длительный эксперимент.

Ожидаемые 400/401/404 от ошибочных действий корректны. Другой статус или таймаут — неожиданный отказ. У soak порог отказов <1%; ramp/stress допускают перегрузку, чтобы её измерить. Во всех сценариях обязательны измеренные запросы и завершённые сессии.

## Артефакты

Каждая серия получает каталог `perf-results/<UTC-время>-<id>/`, каждый сценарий — вложенный каталог. Старые результаты не перезаписываются.

- `environment.json`, `dataset.json`, `results.json` — контекст стенда, тестовые сущности и коды завершения сценариев.
- `samples.json.gz`, `k6.log`, `run.json`, `analysis.log` — исходные точки и диагностика сценария.
- `http.json` — HTTP-статусы, отказы, точные перцентили по шагам, сессии и байты стрима фазы measure.
- `summary.json`, `throughput.json`, `resources.json` — сводки k6, RPS/сессии/байты и ресурсы контейнеров. PostgreSQL включает primary и обе реплики; CPU указан в ядрах, RAM — в байтах.
- `knee.json`, `recovery.json` — устойчивые ступени ramp и восстановление stress.
- `series/`, `plots/`, `compare/` — сохранённые временные ряды, семь PNG и числовое сравнение soak в compare.json.

HTTP-отчёт строится по исходным точкам, без зависимости от доставки remote write. Метрики Kubernetes использует Prometheus/cAdvisor по всем namespaces; CPU/RAM отдельного Docker k6/Prometheus и общего Minikube пишет observers.py через docker stats. Сохранённые серии позволяют повторить анализ после остановки наблюдения. Отсутствие запросов, сессий или CPU/RAM является ошибкой анализа. Ошибочные/незавершённые прогоны не сравниваются как успешные.

Перцентили ступени считаются по её запросам, а не средним оконным p95. Временные графики используют 1-секундные окна. Устойчивая ступень: отказы <1%, p95 ≤ `LATENCY_SLO_MS` (по умолчанию 500 мс), RPS растёт с VU. Относительный скачок p95 — предупреждение, а не самостоятельное доказательство предела. Если все ступени прошли, `capacity_found=false`: определён максимум проверенной нагрузки, а не предел системы. Для восстановления требуется полное окно после перегруза с отказами <1% и p95 ≤1.2 от базы. Quick даёт предварительную оценку, а не доказанную производственную ёмкость.

## Изоляция CPU

По умолчанию runner не меняет CPU minikube. `sudo ISOLATE_CPUS=1 make -C backend perf-run ...` включает существующий механизм cpuset/systemd **после** preflight. В этом режиме minikube получает 0–3, k6 — 4–5, наблюдение — 6–7 при ≥8 CPU; при 4–7 CPU генератор и наблюдение получают по одному CPU. Уборка возвращает исходный cpuset. Диск и память остаются общими; cpuset не запрещает прочим процессам хоста работать на тех же CPU.

## Три прогона и обязательные графики

`make -C backend perf-run PROFILE=quick SCENARIO=trio` выполняет ramp → stress → soak без ошибочных действий. С текущими шестью ступенями ramp это 5 минут нагрузки в quick и 30 минут в full, плюс seed, завершение итераций и анализ. Выполнение последовательное: одновременные эксперименты на одном стенде смешали бы нагрузку. `all` сохраняет пять прогонов, включая ещё два soak с ошибками.

В `plots/`: `latency_over_time.png` показывает p50/p90/p99 во времени; `latency_distribution.png` — распределение запросов по рангу с отметками всех пяти перцентилей; `latency_percentiles.png` — столбцы p50/p75/p90/p95/p99. p75 и p95 по-прежнему рассчитываются и сохраняются в отчёте и JSON; p95 используется при проверке SLO; `latency_histogram.png` — число запросов в интервалах задержки. Все построены по phase=measure. Время запроса — HTTP-отправка/ожидание/получение, без пауз пользователя; это не длительность всей пользовательской сессии.

## Чтение отказов и восстановления

В plots/ остаются только latency_over_time, latency_distribution, latency_percentiles, latency_histogram, cpu_over_time, ram_over_time и rps_over_time. RPS, ошибки, I/O и прочие числовые данные сохраняются без дополнительных графиков. Старые известные лишние PNG удаляются при повторном анализе; исходные измерения не удаляются.

`report.md` — читаемая сводка; `knee.json` содержит VU, общий HTTP RPS, API RPS без прямых S3-запросов, p95, ошибки, причины нарушения и проблемные операции каждой ступени. `windows.json` содержит те же HTTP-операции по 1-секундным окнам. В `http.json` у шагов есть статусы и неожиданные отказы. Это позволяет отличить, например, отказ ленты от отказа загрузки файла.

`recovery.json`: базовый p95 рассчитывается по первой фазе stress без прогрева. После возврата к базовому VU ищется первое полное 1-секундное окно с ошибками <1% и p95 ≤1.2 от базы. Время считается от снятия перегруза до конца этого окна, с шагом 1 с. Отсутствующее окно ошибок не считается здоровым. Это одно окно API, без проверки CPU, RAM, Kafka lag или устойчивости на длительном интервале. `overload_degraded=false` означает, что ухудшение по этому критерию вообще не было зафиксировано. `recovered=false` означает отсутствие подтверждения за 60 с quick / 240 с full после перегруза, а не доказательство вечного отказа.

Нагрузочный runner сейчас запускает отдельный Prometheus и kubectl proxy, без отдельной Grafana. Prometheus нужен для cAdvisor CPU/RAM и получает remote write k6; PNG создаёт plot.py. Обычный Prometheus/Grafana/Loki/Tempo — постоянная наблюдаемость приложения; runner их не выключает и не включает.

`recovery_mode=first_healthy_1s_window` явно обозначает способ расчёта. Поле `relapse_windows` сохраняет последующие окна с новым превышением порога, `no_observed_relapse=false` не позволяет путать первое здоровое окно с устойчивым восстановлением.

График rps_over_time.png возвращён по запросу: X — секунды, Y — завершённые HTTP-запросы/с за 1-секундное окно; отдельные линии показывают все HTTP и только API без прямого S3. На временных графиках длительности фаз вынесены в верхнюю полосу, значимые события обозначены цифрами с расшифровкой под графиком; вертикальные подписи не накладываются.

Частота сбора тестового Prometheus и iostat — 1 секунда; шаг временных графиков — 1 секунда. CPU рассчитывается через rate за 30 секунд: это сглаженная загрузка, а не мгновенное значение. Частота обновления исходных счётчиков cAdvisor может быть ниже частоты опроса. HTTP-тайм-аут k6 в пользовательских сценариях — 5 секунд; превышение учитывается как ошибка, а не удаляется из статистики. Настройки применяются к новым прогонам.

## Как оценить пропускную способность

Отдельного режима с заданным RPS нет. В `ramp` k6 повышает число виртуальных пользователей, а `knee.json` записывает для каждой ступени фактические VU, HTTP RPS, API RPS, p95 и отказы. `rps_over_time.png` показывает достигнутый поток запросов по секундам. Ступень считается устойчивой при неожиданных отказах <1% и p95 ≤ `LATENCY_SLO_MS`; смотри также, продолжает ли фактический RPS расти при добавлении VU.

Последняя ступень, прошедшая эти критерии, — измеренный RPS для пользовательской смеси и выделенных ресурсов. Если прошли все ступени, предел не найден: проверен только максимум сетки VU. Если следующая ступень не прошла, граница лежит между фактическим RPS последней устойчивой и первой неустойчивой ступени. Ступени задаются массивом `levels` в `loadtest/perf/session.js`, их длительность — `RAMP_STAGE_SEC` (по умолчанию 20 секунд в quick и 100 в full); для уточнения добавь значения между последней устойчивой и первой неустойчивой ступенью и повтори `ramp`. Затем проверь выбранный рабочий уровень отдельным долгим `soak`; это будет нагрузка в VU с фактическим RPS, а не фиксированная цель RPS.

VU и RPS нельзя приравнивать. Приблизительно `RPS = VU × запросов за итерацию / среднее время итерации в секундах`; время итерации включает паузы пользователя и ответы API. При замедлении сервиса закрытая модель k6 сама уменьшает частоту запросов на пользователя. Поэтому итоговый RPS берётся из измерений, а не из умножения VU на постоянный коэффициент.

## Исправления перед повторным ramp

Для серии 20261119T205902Z-b32ac2 статус Kubernetes подтвердил последнее завершение RustFS: OOMKilled, exit 137, 2026-11-19T21:11:03Z, при лимите 512Mi. Счётчик 14 — накопленный за жизнь старого пода, а не число рестартов только в этом тесте. В манифесте RustFS request памяти поднят до 512Mi, limit до 2Gi. Это увеличение бюджета, а не доказательство отсутствия утечки памяти; устойчивость под нагрузкой проверяется отдельным пользовательским запуском.

В author загрузка и публикация нового трека теперь проверяются до использования в плейлисте. При их сбое сценарий использует готовый seed-трек; исходная ошибка upload/publish остаётся неожиданной и не маскируется. Непубликованный собственный трек удаляется своим ID. Ранее failed upload оставлял trackID нового pending-трека, а следующий playlist-add закономерно возвращал 409 (track is not ready). В сохранённой серии 513 неудачных upload сопровождались 513 ответами 409.

Сбор CPU/RAM теперь выбирает максимум по pod/container перед суммой по контейнерам сервиса: старые cAdvisor-ряды предыдущих экземпляров после рестартов не должны складываться с текущим экземпляром. Старые агрегаты не содержат ID контейнеров, поэтому их нельзя точно исправить задним числом. Диагностика ошибок дополнительно сохраняет container-terminations.json с причиной, временем завершения и restartCount.

## Автоматический HTML на всю серию

Каждый `perf-run` создаёт `perf-results/<серия>/report.html`. Файл обновляется после каждого выполненного этапа и в `finally` после уборки, включая ошибку preflight, k6 или анализа. В нём находятся только реально существующие сценарии: ramp, stress, soak с разными FAULT_RATE. Если серия прервалась, готовые данные отображаются вместе с причиной прерывания. Каждая картинка занимает одну строку на всю ширину; внешние серверы и интернет для просмотра не нужны.

Для каждого сценария в HTML доступны таблицы HTTP, ступени, ошибки, восстановление stress, графики задержек/RPS и раздел CPU/RAM. Раскрой имя контейнера, чтобы увидеть два отдельных графика по всей ширине. Kubernetes-метрики теперь собираются по всем namespaces и хранят namespace/pod/container в `series/cpu_detailed.json` и `series/ram_detailed.json`. Поэтому PostgreSQL primary/реплики, exporters, ingress, DNS, управляющие компоненты Kubernetes и активный мониторинг различимы. Это статистика контейнеров, не профилирование каждого PID/процессов ядра хоста.

`docker-resources.json` хранит CPU/RAM тестового Prometheus, k6 и контейнера Minikube. Пауза между вызовами Docker CLI — 1 с, к ней добавляется время команды; фактическое время каждой точки записано. Minikube total включает Kubernetes-поды, складывать эти графики нельзя. cAdvisor опрашивается каждую секунду, CPU рассчитывается rate за 30 с; RAM — working set. Отсутствующие данные отмечаются явно, а не заменяются нулями.

`hardware.json` содержит снимок соответствия логических CPU физическим ядрам. `pods-before.json` / `pods-after.json` каждого этапа сохраняют UID, readiness, resources, restartCount и последнее завершение без env/секретов. HTML сравнивает счётчики для одного UID, показывает новые поды отдельно и не считает исторические рестарты новыми. Мгновенные сбои готовности между снимками и уже исчезнувшие поды могут быть не видны.

Пересобрать HTML по сохранённым данным без запуска нагрузки:

```bash
python3 deploy/perf/report.py perf-results/<серия>
```

Пересчитать графики по сохранённым k6 samples и рядам, затем обновить HTML:

```bash
MPLCONFIGDIR=/tmp/chimera-mpl-cache python3 deploy/perf/plot.py run perf-results/<серия>/<сценарий>
python3 deploy/perf/report.py perf-results/<серия>
```

Без `PROM_URL` анализатор работает офлайн. Сохранённые метрики старой серии не становятся подробнее после пересборки: namespace/pod и метрики Docker можно получить только в следующем пользовательском запуске. Лимит расчёта после нагрузки — `ANALYSIS_TIMEOUT=300` секунд; окна HTTP индексируются заранее, чтобы длительный soak не требовал повторного полного просмотра samples на каждую секунду.

## Готовый trio с уменьшенными файлами

Текущая сетка ramp — 100, 200, 300, 400, 500, 650 VU. Stress использует базу, найденную ramp, затем `ceil(база × 1.6)`, затем базу. По умолчанию TRACK_BYTES=65536 (64 КиБ), а не прежние 256 КиБ. Это снижает сетевой/дисковый объём загрузок в четыре раза при том же числе загрузок, но меняет состав нагрузки: цифры с прежним размером файла нельзя считать полностью сопоставимыми. Потребление RAM и возможность OOM этим не гарантируются.

```bash
ISOLATE_CPUS=1 WARMUP_SEC=30 RAMP_STAGE_SEC=100 SOAK_DURATION=10m TRACK_BYTES=65536 LATENCY_SLO_MS=500 make -C backend perf-run PROFILE=full SCENARIO=trio
```

Это 10 минут ramp + 10 минут stress + 10 минут soak, плюс подготовка, завершение запросов и анализ.
