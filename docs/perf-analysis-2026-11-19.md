# Разбор и исправление нагрузочного тестирования — 19 ноября 2026

## Причина ожидания пода

Ожидался primary PostgreSQL. Его внешний startupProbe допускал долгий запуск, но primary.sh независимо завершал сервер после 120 попыток с паузой 1 с. В предыдущем логе есть `primary did not become ready`, затем smart shutdown во время восстановления. Это не зависание k6: генератор ещё не запускался.

Холодная инициализация и fsync на этом диске занимали минуты. Скрипт принудительно завершал корректно запускающийся сервер; после перезапуска PostgreSQL снова синхронизировал и восстанавливал данные. Увеличение таймаута kubectl или startupProbe не устраняло внутренний watchdog.

## Другие фундаментальные ошибки

- Оркестратор измерения одновременно развёртывал стенд, отключал наблюдение, очищал хранилища и заново клонировал реплики перед каждым сценарием. Ошибка подготовки превращалась в длительное ожидание подов.
- Реплика копировалась прямо в PGDATA; наличие PG_VERSION ошибочно означало успешное завершение pg_basebackup. На самом деле файл появляется в начале копирования.
- pg_basebackup использовал медленный checkpoint по умолчанию. При восстановлении двух реплик это добавляло ожидание.
- Код завершения k6 терялся при перенаправлении stdout docker wait; отчёт мог объявить успех после ошибки setup.
- Относительный рост p95 на коротких ступенях ошибочно трактовался как предел производительности при продолжающемся росте RPS и нулевых отказах.

## Что изменено

- Primary передаёт PID 1 официальному docker-entrypoint через exec. Роль и HBA для репликации создаются официальным init-hook до старта TCP-сервера. Отдельного watchdog больше нет.
- Реплика использует --checkpoint=fast, копирует во временный каталог и атомарно публикует только завершённую копию. Неполный старый PGDATA отклоняется с понятной ошибкой.
- runner.py проверяет уже готовый стенд, один раз создаёт уникальный dataset, последовательно измеряет сценарии и удаляет только собственные контейнеры/процессы и тестовые аккаунты. Он не применяет Kubernetes-манифесты, не масштабирует приложения и не очищает PVC. Подготовка и восстановление конфигурации — отдельные команды.
- Preflight ограничен по времени, CrashLoop даёт ранний отказ и диагностику. При первой ошибке серия прекращается. Сбой анализа отделён от кода k6.
- HTTP-статистика строится по сохранённым точкам фазы measure, без seed/прогрева. Метрики ресурсов сохраняются для повторного анализа без Prometheus.
- Порог ramp теперь явно задан: p95 ≤500 мс (LATENCY_SLO_MS), ошибки <1%, RPS растёт. Относительные скачки отмечаются предупреждением. Прохождение последней ступени не называется найденным пределом.

## Единственный контрольный прогон после переписывания

Команда: `make -C backend perf-run PROFILE=quick SCENARIO=ramp`. Использован готовый minikube, инфраструктура не пересоздавалась. Seed: 50 пользователей, 40 треков по 256 КиБ, 5 плейлистов. База — primary и две реплики; по три пода Gateway/Identity/Catalog/Social, два edge. У minikube сохранён имевшийся cpuset 0–3; новая CPU-изоляция не включалась. Внутрикластерное наблюдение не перенастраивалось. Старые внешние наблюдатели работали во время измерений и удалены после него; это ограничивает сопоставимость с полностью изолированным прогоном.

Измерено **8027 запросов**, **1037 завершённых сессий**, неожиданных отказов **0**. Среднее **38.82 мс**, p50 **1.68 мс**, p95 **233.99 мс**, p99 **475.45 мс**. k6 и анализ завершились кодом 0. Завершено 1037 итераций, прерванных 0.

## Где растут задержки

| Шаг | p95, мс |

| feed | 3.39 |

| login | 285.71 |
| create | 387.73 |
| playlist-add | 416.56 |
| track-delete | 465.64 |
| upload | 691.51 |

Чтения быстрые; задержки сосредоточены на входе и записи, особенно загрузке в RustFS. Identity потреблял больше всего CPU среди Go-сервисов: максимум около 0.73 ядра. По этим данным нет признаков исчерпания четырёх CPU приложения.

На хостовом sda средняя занятость в собранных iostat-окнах около 63%, максимум 93.2%. Медленные fsync при загрузке PostgreSQL и рост задержек записи согласуются с влиянием диска. Это гипотеза о причине задержек, а не доказанный единственный bottleneck: iostat включает сторонние процессы хоста, а точные ожидания PostgreSQL/S3 отдельно не измерялись.

Рост RAM RustFS в коротком тесте нельзя считать утечкой: это может быть прогрев и кэш. Длительный soak и stress здесь намеренно не запускались. После прогона все поды приложения/БД готовы, контрольное чтение удалённого тестового пользователя возвращает 404.

## Проверка изменений

15 автоматических тестов, shell-синтаксис, Python compile и git diff --check прошли. k6 inspect прошёл. Успешно выполнен один настоящий quick-ramp и повторный офлайн-анализ тех же точек. Новые PostgreSQL entrypoint проверены тестами; полный холодный старт на пустых томах после переписывания не повторялся, чтобы не возвращаться к циклу очисток и перезапусков.

Порядок дальнейшего использования: `make -C backend perf-prepare` один раз при необходимости применить конфигурацию, затем `make -C backend perf-run PROFILE=quick SCENARIO=...`. Обычную конфигурацию возвращает `make -C backend perf-restore`. Важное отличие: perf-run больше не занимается подготовкой/сбросом инфраструктуры.
