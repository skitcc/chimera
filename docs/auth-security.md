# Аутентификация и BDD E2E

Обычное приложение использует обязательный второй фактор: пароль и одноразовый
email-код. Срок действия кода — 5 минут, повторная отправка — через 60 секунд.
Пять ошибок пароля или кода суммарно блокируют вход на 15 минут. Правильный
пароль не сбрасывает счётчик: его сбрасывают завершённый вход и восстановление.
Планового истечения пароля нет; пользователь меняет пароль вручную.

## HTTP API

- `POST /v1/users`: регистрация без JWT.
- `POST /v1/sessions` с `email`, `password`: `202`, `challenge_id`, `expires_at`
  (Unix seconds); JWT отсутствует.
- `POST /v1/sessions/verify` с `challenge_id`, `code`: `201`, прежняя форма
  успешной сессии (`token`, `user_id`).
- `POST /v1/password-recovery` с `email`: одинаковый `202` и общий `message`
  для существующего и неизвестного email, в том числе при cooldown и ошибке SMTP.
- `POST /v1/password-recovery/verify` с `email`, `code`, `new_password`: `204`.
  После восстановления необходимо войти заново с обоими факторами.
- `POST /v1/password-change` с Bearer JWT и `current_password`: `202`,
  `challenge_id`, `expires_at`.
- `POST /v1/password-change/verify` с Bearer JWT, `challenge_id`, `code`,
  `new_password`: `204`; этот JWT и все остальные старые JWT отзываются.
- `GET /v1/session` с Bearer JWT: `204`, если сессия ещё действительна.

Новый пароль должен отличаться от текущего и содержать минимум 8 байт, как и
при регистрации. В защищённом режиме `PATCH /v1/users/{id}` с `password`
отклоняется. Gateway проверяет версию авторизации JWT через Identity primary
при каждом защищённом запросе и запросе с необязательным JWT. Если primary
недоступен, запрос отклоняется с `503`; устаревшая версия даёт `401`. Frontend очищает отозванную
сессию и переводит пользователя на страницу входа.

Проверки, HMAC кодов, счётчики ошибок и версия авторизации хранятся в Identity
PostgreSQL. Операции сериализуются блокировкой аккаунта; отказ по неверному
паролю/коду сохраняет счётчик, инфраструктурная ошибка откатывает транзакцию.
SMTP-доставка ограничена тайм-аутом. При её сбое вход не завершается. Смена и
восстановление пароля повышают версию и удаляют все незавершённые проверки.
Новые изменяющие auth RPC не повторяются автоматически после тайм-аута.

## Конфигурация

`AUTH_SECURITY_ENABLED` по умолчанию включён в Identity и Gateway. Identity
требует общий для всех реплик `AUTH_CODE_HMAC_KEY` минимум 32 байта. Для dev:

```sh
export AUTH_CODE_HMAC_KEY=$(openssl rand -hex 32)
docker compose up --build -d
```

Сохраните ключ в локальном окружении/секрете, если стенд должен переживать
перезапуск с незавершёнными проверками. В Kubernetes ключ генерирует
`make -C backend k8s-secrets`; применяйте конфигурацию только после завершения
текущего perf-прогона.

Compose использует Mailpit: UI/API доступен только на `127.0.0.1:8025`, SMTP —
внутри сети. Gateway не публикует API перехватчика. В изолированном E2E-стенде
Mailpit вообще не публикует host-порты. В Kubernetes Mailpit доступен только
как внутренний Service. Для `k8s-e2e` в защищённом режиме сначала выполните
`kubectl -n chimera port-forward svc/mailpit 8025:8025`. Ручные команды
`demo-requests`, `e2e-dev`, `k8s-e2e` принимают `DEV_MAILPIT_URL` (по умолчанию
`http://127.0.0.1:8025`); для частного Compose URL задаётся автоматически.
Для настоящей почты задайте `SMTP_ADDR=host:port`, `SMTP_FROM`, `SMTP_USERNAME`,
`SMTP_PASSWORD`, `SMTP_REQUIRE_TLS=true`. Поддерживается STARTTLS; прямое
implicit TLS соединение на порту 465 не используется.

## Проверки

### Соответствие заданию

| Требование | Подтверждение |
| --- | --- |
| BDD E2E аутентификации | Godog выполняет `backend/e2e/features/auth.feature` через настоящий Gateway, Identity, PostgreSQL и SMTP/Mailpit |
| Два фактора | Пароль без email-кода не открывает защищённую операцию; правильный код завершает вход |
| Ограниченное количество попыток | Четыре ошибки допускают вход; пятая блокирует. Ошибки пароля и кода учитываются суммарно |
| Восстановление после блокировки | Email-код и новый пароль снимают блокировку; повторный вход требует 2FA |
| Плановая смена пароля | Ручная смена с текущим паролем и email-кодом отзывает старый пароль и JWT |
| Технический пользователь | Отдельный пользователь на сценарий, удаление пользователя и писем в After hook, включая падение сценария |
| CI без паролей в исходниках | Пароли технических пользователей берутся из GitHub Actions Secrets; отчёты очищаются перед upload |

Файл содержит 13 сценариев. Дополнительный тест намеренно проваливает вложенный
сценарий и проверяет очистку. Инфраструктурные секреты изолированного стенда
генерируются на каждый запуск. Загрузка артефактов разрешена только после успешной
очистки диагностических файлов.

### Пароли в GitHub Actions Secrets

В репозитории откройте Settings → Secrets and variables → Actions и создайте
два repository secrets с разными случайными однострочными паролями
(рекомендуется 16–64 ASCII-символа; допустимо 8–72 байта):

- `E2E_USER_PASSWORD`: начальный пароль технических пользователей.
- `E2E_NEW_PASSWORD`: пароль после смены или восстановления.

CI передаёт `${{ secrets.E2E_USER_PASSWORD }}` и `${{ secrets.E2E_NEW_PASSWORD }}`
в окружение jobs `system`, `e2e`, `auth-e2e`. Runner передаёт их тестовому
контейнеру через `docker run -e ИМЯ`, без значений в командной строке.
Тест регистрирует пользователя через `POST /v1/users` с начальным паролем,
входит через `/v1/sessions`, а новый пароль отправляет через API смены или
восстановления. Identity получает обычные запросы и сохраняет bcrypt-хеш.
Приложение не подключается к GitHub и не получает доступ к repository secrets.
Email и пользователь остаются отдельными для каждого сценария и удаляются
после него; хранить постоянного пользователя в БД не нужно.

В GitHub Actions отсутствие секрета или одинаковые пароли — ошибка подготовки,
случайного fallback там нет. Secrets недоступны обычным PR из внешних forks:
такой прогон требует доверенного запуска с доступом к secrets. Для локального
запуска можно экспортировать оба значения в окружение; если оба отсутствуют,
тест генерирует одноразовую пару. Не добавляйте значения в `.env.example` или Git.

### Запуск

```sh
cp .env.example .env  # только при первом запуске, не заменяйте свой .env
make -C backend test-auth-e2e
make -C backend test-e2e
make -C backend test-auth-perf-compat
make -C backend allure-results
make -C backend allure-open
```

Команды создают отдельные Compose-проект, сеть, тома и JWT-ключи. Пароли БД,
объектного хранилища и HMAC-ключ генерируются на каждый запуск. В CI они
маскируются через `add-mask`; пароли пользователей в CI поступают из двух
repository secrets, описанных выше.
Каждый BDD-сценарий создаёт собственного технического пользователя. After hook
удаляет его и письма даже при ошибке и проверяет очистку. Доступ теста к primary
используется только для очистки и моделирования истечения кода; проверки
поведения выполняются через настоящий HTTP Gateway и SMTP.

Результаты: `backend/auth-bdd/junit.xml`, `backend/auth-bdd/cucumber.json`,
`backend/allure-results`. Allure хранит названия сценариев и статусы, без тел
HTTP/SMTP, кодов, паролей и JWT. Диагностика перед upload проходит
`backend/scripts/sanitize-auth-artifacts.py`: структурированные секреты,
JWT, OTP и известные секреты окружения заменяются; сырые pcap удаляются,
поскольку безопасная редакция бинарного захвата не гарантируется.

`allure-results` запускает unit и integration, затем все обычные E2E вместе
с BDD (`test-e2e`) и отдельно perf-совместимость без нагрузки. Все результаты
пишутся в один `ARTIFACTS_DIR`. Для integration сначала нужен `make -C backend
stand-up`. В Allure раздел `End to end` содержит демо, smoke, `Authentication
BDD` (13 сценариев и проверка очистки) и perf-совместимость. `allure-open`
перестраивает HTML из результатов; один запуск `allure-results` HTML не обновляет.

### Grafana и Prometheus

В Kubernetes манифесты задают по одной реплике, но ранее выключенные deployments
можно поднять без обновления приложения командой `make -C backend
k8s-monitoring-up`. Она удерживает `.perf-run.lock`, включает только Grafana
и Prometheus и ждёт их готовности. Grafana: `/monitoring/`; Prometheus доступен
через port-forward из `make -C backend k8s-monitoring`. Loki, Tempo и Collector
эта команда не запускает: для логов и трасс их нужно включать отдельно.

Unit-тесты правил находятся в `identity/internal/usecase/security_test.go`,
PostgreSQL-тест конкурентных попыток и одноразовости — в
`identity/internal/infra/postgres/security_integration_test.go`. Обычная
команда `make -C backend test-integration INTEGRATION_SERVICES=identity`
включает этот тест.

`test-auth-perf-compat` выполняет только проверку старого одноэтапного входа,
изменения пароля через профиль и прежнего поведения JWT в отдельном Compose.
Нагрузка не запускается. `AUTH_SECURITY_ENABLED=false` установлен явно только
в perf-конфигурациях (`deploy/k8s/overlays/perf` и no-load Compose overlay).
Сценарии нагрузки, runner и расчёты отчётов этим изменением не затронуты.
E2E-команды отказываются запускаться, пока занят `.perf-run.lock`.
