# Устойчивость к недоступности

Прогон `make k8s-chaos` 15 ноября 2026 против edge в minikube
(`http://chimera.192.168.49.2.nip.io`). Скрипт `deploy/scripts/chaos.sh`,
нагрузка на время удаления пода — `loadtest/resilience.js`. После прогона
Catalog снова в трёх подах, реплики Postgres — в двух.

## Что происходит по фазам

1. Пока k6 читает ленту, удаляется один под Catalog. Клиент gRPC повторяет
   `UNAVAILABLE` на другом поде (`round_robin`, до 3 попыток).
2. Catalog масштабируется до нуля. Лента отвечает `503` в пределах тайм-аута
   клиента. Вход остаётся на Identity и проходит. `DELETE` пользователя тоже
   проходит: `UserDeleted` лежит в Kafka, пока Catalog не поднимется.
3. Catalog возвращается. Консьюмер дочитывает событие, черновик пользователя
   исчезает.
4. Реплики масштабируются до нуля. Чтение ленты, не получив реплику, идёт на
   primary и остаётся `200`.

## Прогон

k6: 10 виртуальных пользователей, 40 секунд, под Catalog удалён на 12-й секунде.
Код выхода k6 — 0, порог скрипта — меньше 5 ответов 5xx.

| Фаза | Наблюдение |
| --- | --- |
| Удаление одного пода Catalog | 1980 ответов ленты, 0 ошибок, p(95) 2,02 мс |
| Catalog выключен | `GET /api/v1/tracks` — 503, `POST /api/v1/sessions` — 201, `DELETE /api/v1/users/{id}` — 204 |
| Catalog снова в трёх подах | черновик удалённого пользователя стал 404 |
| Реплики выключены | `GET /api/v1/tracks` — 200 |

Повторы gRPC видны метрикой `chimera_grpc_client_retries_total` и событием
`grpc.retry` в спане. Grafana на `/monitoring` открывает дашборд Chimera и
связывает строку лога с трейсом по `trace_id`.
